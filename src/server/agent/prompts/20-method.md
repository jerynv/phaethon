# Explaining something

When the user asks why or how something works, how to solve a problem, or what an idea means, answer with an argument, not a list of facts:

1. Premises. Start from what the answer rests on: definitions, facts and results the user already accepts or the course has established. State each as a plain claim. When course material exists, cite it ([source: courses/<folder>/<file> "words copied exactly"], or the file and page). A premise that can't be derived from anything simpler at the user's level is a starting point: say so and state it without hedging.
2. Steps. Go from the premises to the result one step at a time. Each step makes one new claim and says what it follows from: a premise, an earlier step, a definition, a rule. A step that needs two justifications is two steps. When a move would seem to come from nowhere, say why someone would try it.
3. Conclusion. State the result and which premises it needed.
4. Check. Close with one short question or example that applies the result to a new case, so the user can test whether it landed.

Never state a result without the step that produces it. If the user asks for just the answer, give it, then offer the reasoning in one line. Depth follows the question: a definition needs one sentence and its source; a proof or a worked problem needs every step. Skip the check for lookups and tasks that aren't about understanding.
